# RB-000: Pre-Change Baseline Backup

**Before starting any phase, run this procedure.**

## Backup steps

```bash
# 1. Create a git tag for the current state
git tag pre-redesign-$(date +%Y%m%d) -m "State before redesign — baseline"

# 2. Copy the SQLite database
cp local-server/data/eagle-insight.db local-server/data/eagle-insight.db.backup-$(date +%Y%m%d)
cp local-server/data/eagle-insight.db-shm local-server/data/eagle-insight.db-shm.backup-$(date +%Y%m%d)
cp local-server/data/eagle-insight.db-wal local-server/data/eagle-insight.db-wal.backup-$(date +%Y%m%d)

# 3. Export localStorage state (run in browser console before any changes)
# In browser console:
# JSON.stringify({csvData: localStorage.getItem('csvData'), snapshots: Object.keys(localStorage).filter(k=>k.startsWith('snapshot_')).map(k=>({key:k,data:localStorage.getItem(k)}))})
# Save the output to a file.
```

## Recovery from baseline

```bash
# 1. Restore git state
git checkout pre-redesign-{date}

# 2. Restore SQLite database
cp local-server/data/eagle-insight.db.backup-{date} local-server/data/eagle-insight.db

# 3. Rebuild and restart
cd local-server && npm run build && node dist/index.js
npm run dev
```

# RB-001: Rollback — Server-Side Rule Evaluation

**Change:** Move rule evaluation from client-side browser to server-side `rules-service`  
**Phase:** 1.1  
**Risk level:** High (changes how all findings are generated)  
**Affected files:** `local-server/src/services/rules-service.ts`, `local-server/src/routes/rules-api.ts`, `local-server/src/services/ingestion-service.ts`, `src/contexts/CSVDataContext.tsx`  
**Affected data:** `findings` table, `rule_execution_results` table (new)

## Pre-change backup

- Run RB-000 baseline procedure
- Export all findings: `GET /api/findings?limit=9999` and save JSON

## Rollback trigger criteria

- Rule evaluation completes but generates no findings where previously it did
- Rule evaluation silently fails (no error, no findings, no execution results)
- Finding quality degrades (wrong severity, wrong aircraft linkage)
- Performance regression: ingestion takes >30 seconds where it previously took <5

## Rollback steps

```bash
# 1. Revert server-side changes
git checkout pre-redesign-{date} -- local-server/src/services/rules-service.ts
git checkout pre-redesign-{date} -- local-server/src/routes/rules-api.ts
git checkout pre-redesign-{date} -- local-server/src/services/ingestion-service.ts

# 2. Revert frontend changes
git checkout pre-redesign-{date} -- src/contexts/CSVDataContext.tsx

# 3. Rebuild both
cd local-server && npm run build
npm run build

# 4. Restart server
node local-server/dist/index.js
```

## Data recovery

If new findings were created by the server-side engine but are duplicates of client-side ones, clean up via:
```sql
-- Review findings created after the change date
SELECT * FROM findings WHERE created_at > '2026-XX-XX' AND generated_by = 'rules-engine';
-- Delete duplicates if both sets exist:
DELETE FROM findings WHERE generated_by = 'rules-engine' AND created_at > '2026-XX-XX';
```

## Validation after rollback

- Upload a test CSV
- Confirm findings appear in the UI (client-side evaluation working)
- Confirm `rule_execution_results` table does not have new entries (server eval stopped)

## Known rollback limitations

- Any findings created by the server-side engine that were acknowledged or had tasks created will lose their findings records if deleted
- Recommendation: do not delete findings with `status != 'new'` — instead mark them `rejected` with note "generated by rollback-cancelled server evaluation"

## Re-migration safety

Re-applying server-side rule evaluation after rollback is safe if:
- `rule_execution_results` table was properly cleared
- Deduplication logic is confirmed working before retry

# RB-002: Rollback — Evidence Persistence to Server

**Change:** Move selectionSets and evidence from localStorage to SQLite via evidence API  
**Phase:** 1.2  
**Risk level:** Medium (affects data an engineer created in the investigation workbench)  
**Affected files:** `src/contexts/CSVDataContext.tsx`, `local-server/src/routes/` (new evidence route), `local-server/src/services/` (new evidence service)  
**Affected data:** `evidence_items` table (new), localStorage `csvData` key

## Pre-change backup

- Run RB-000
- Export localStorage in browser before starting (see RB-000 step 3)
- Export evidence from new server table before rollback: `GET /api/evidence?limit=9999`

## Rollback trigger criteria

- Evidence items created by engineers are not persisting to server
- Evidence loads incorrectly or is missing after page reload
- API errors on evidence creation

## Rollback steps

```bash
# 1. Revert CSVDataContext to localStorage version
git checkout pre-redesign-{date} -- src/contexts/CSVDataContext.tsx

# 2. Revert or remove new evidence routes
git checkout pre-redesign-{date} -- local-server/src/routes/
git checkout pre-redesign-{date} -- local-server/src/services/

# 3. Rebuild
cd local-server && npm run build
npm run build
```

## Data recovery

Evidence items created in the server during the trial can be exported:
```bash
curl http://localhost:3001/api/evidence?limit=9999 > evidence-export-$(date +%Y%m%d).json
```

Restore to localStorage manually if needed (this is the downside of the rollback — server evidence doesn't automatically re-populate localStorage).

## Validation after rollback

- Open engineering portal
- Create a selection set
- Refresh page
- Confirm selection set survives page reload (localStorage working)

# Business Continuity During Rollback

For any rollback that affects findings or tasks:

1. **Do not delete acknowledged or in-progress findings** — even if they were created by a system that is being rolled back
2. **Preserve the audit log** — audit entries from the rolled-back period remain and are informative
3. **Notify active users** — if multiple engineers are using the system, notify them before rollback
4. **Verify data integrity after rollback** — run: `GET /api/findings?limit=50` and confirm the list matches pre-change state
5. **Document the rollback** — add a note to the audit log: "System rollback performed on [date] by [user] — reason: [reason]"
   ```bash
   curl -X POST http://localhost:3001/api/audit \
     -H "Authorization: Bearer {token}" \
     -d '{"action":"system.rollback","entityType":"system","entityId":"rollback","note":"Rollback: RB-00X performed — reason"}'
   ```
